## 1. What this arc IS

An engineering substrate arc that fixes two harness classification bugs the S2905-S2908 sweep cycle surfaced as a systemic drift pattern:

- **T1 — Harness soft-error classifier fix.** `pa_tool_validate_harness._run_single_action` currently classifies any `ToolResult.ok=True` as `expected_outcome='success'`, even when the response body contains an inline `{ok:false, error, error_code}` envelope (transport succeeded but the tool signalled application-layer failure). Introduce new stable `expected_outcome='soft_error'` value. Bump `HARNESS_VERSION` `v1` → `v2`. Backfill: rerun harness across all 15 sweep-covered tools inside T1 (backfill IS the T1 evidence).
- **T2 — Bridge availability precheck.** External-bridge-dependent tools (OBS bridge, resolve_node) currently return `bridge_unreachable` envelopes at harness time with no preflight distinguishing "bridge down at env-config time" vs "real tool bug." Add a cached (once-per-bridge-per-harness-run) preflight probe; on unreachable, short-circuit dependent actions to new stable `expected_outcome='skipped_bridge_unreachable'` value.

Optional post-fix experiment (deferred, requires separate Chris D-verdict after T1+T2 ship):

- **T3 — Reverse-control uniform-READ_ONLY sweep batch.** One clean batch to quantify whether drift-rate drops below 50% post-remediation. If yes → confirms Rigby's batch-selection-bias hypothesis fully. If no → drift is more systemic than the classifier fix explains; escalates to Playbook amendment territory (Testing Discipline chapter candidacy — Ledger row 154).

## 4. Fold-log from Rigby SIGN T0 zoom-out (2026-07-23)

Four SIGN questions; Q1-Q3 AGREE; Q4 named a substantive coupling risk folded into arc shape.

- **Fold Q1 (semantics) → T1 design constraint.** `soft_error` and `error_captured` COEXIST. Semantics: `error_captured` = `ToolResult.ok=False` (dispatcher-layer error, no result dict). `soft_error` = `ToolResult.ok=True` AND `isinstance(result.result, dict)` AND (`result.result.get('ok') is False` OR `'error_code' in result.result`). Preserves transport-layer vs application-layer distinction.
- **Fold Q2 (bridge precheck cadence) → T2 design constraint.** Once per bridge per harness run, cached in a dict on the harness-runner instance. Additional precision (mid-run bridge flaps) explicitly out of scope; opt-in flag possible in a future substrate row but NOT this arc.
- **Fold Q3 (backfill scope) → T1 evidence constraint.** All 15 sweep-covered tools. Rationale: classifier fix is a contract change (`expected_outcome` set + version bump); evidence should cover the full slice we've claimed "sweep-validated," not only the 4 recently-drifted tools.
- **Fold Q4 (DOC-AUTOGEN coupling risk, `same_pr_mitigatable` + `future_trigger`) → T1 mitigation + T2 mitigation + ledger row.** Per-tool validation docs (`docs/research/tools/validation/*.md`) are hand-authored evidence narratives — the harness does NOT auto-regenerate them. Post-backfill scenario: harness artifacts flip many actions from `success` → `soft_error`, but the validation docs still claim "SUCCESS" in their `Post-merge live-dispatch` sections → NEW parity-gap type (harness↔validation-doc drift, distinct from schema↔doc parity that Fold B already gates on). **Same-PR mitigations (both adopted):** (a) T1 PR description explicitly documents the gap under a `## Known follow-up: doc↔harness parity` heading; (b) `pa_tool_validate_harness` module docstring gains a "Migration notes" block stating validation docs are hand-authored evidence and not auto-updated. **Future-trigger candidate:** lightweight lint that flags `soft_error` in harness artifact + "SUCCESS" claim in matching validation doc. Adds to Rigby Tool Gap Ledger as a follow-up substrate row; NOT built in this arc.

## 6a. Future-trigger notes from post-implementation SIGN (Rigby Q4 zoom-out)

No downstream watcher identified today; noting as operational-ripple future_trigger. If a downstream watcher surfaces, evaluate whether to add a `harness_version` gate on cache-key semantics.
- **FT-2 (`error_code`-key false-positive constraint).** v2 classifier treats *presence* of `error_code` in response dict as failure signal. Today all inspected tools use `error_code` only for error paths. If any tool later emits `error_code` as informational metadata on success, it will be misclassified as `soft_error`. Constraint: **tools must not emit `error_code` on success**. Enforcement: if a false-positive is observed, either (a) narrow the classifier to require `error_code` AND non-empty error value, or (b) codify the constraint as a schema-lint rule.
