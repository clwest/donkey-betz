## Phase 2 — The Actual Architectural Question

**Restated precisely:** Where should the Engineering Playbook — the codification of methodology surfaced during Cycle 1A (PIC-1..10 verbatim in 0199 Appendix D) — physically live, and what is the source-of-truth relationship between its location, its consumers, and the rest of the knowledge system?

**Underneath that surface question, three deeper ones:**

1. **Consumer model.** The Playbook has two structurally different reader populations — (a) governance consumers (Chris ratifies revisions; SIGN cycles review it; provenance matters), (b) operational consumers (Claude at Phase 0 orientation; humans debugging processes). Which consumer is primary determines where it lives.
2. **Immutability model.** Cycle 1A established that ratified engineering records get **immutable-on-write** via workspace `content_tool.content_complete` + PublishGate + `content_hash` (0010 §6). Is that the right immutability substrate for the Playbook, or is Git's cryptographic hash + tag chain sufficient?
3. **Coupling model.** The Playbook mutates. Each PIC codification lands as v1.0 → v1.1 → v1.2. Where does version history live, how does it stay in sync with what session-start bootstrap reads, and how does RAG retrieve the *ratified* version, not the *drafted-in-a-branch* version?

**Challenging the default:** the reflexive answer is "put it in `/docs/` because that's where docs live and where CLAUDE.md points." That answer is wrong until proven right — because `/docs/` is not currently designed as a **governance surface**. It is a knowledge-management surface for operational content. Cycle 1A demonstrably moved constitutional artifacts (ADRs, cycle open/close, ratification records) OUT of `/docs/` and INTO the workspace precisely because `/docs/` lacked the primitives to enforce ratification + immutability. Putting the Playbook back in `/docs/` would reverse that migration for the wrong reason.

### 3.2 Hierarchy / parent-child (as actually used)

**Modeled hierarchy is absent.** Parent-child, sibling, and cycle-membership relationships are **encoded in title strings + workspace membership** only. Examples from primary evidence:

- `0100_CYCLE_1_OPEN` is not linked via `parent_object_id` to `0000_RAR_METHODOLOGY` or `0010_RESEARCH_OPERATING_PROTOCOL` — it merely shares workspace membership.
- `RATIFICATION_20260708_0199_CYCLE_1_CLOSEOUT` is not linked via `parent_object_id` to `0199_CYCLE_1_CLOSEOUT` — link is captured in title string parsing.
- Cycle 0 / Cycle 1 grouping exists only as a mental model: all deliverables are flat rows in the same workspace.

This is not necessarily a defect — it is currently sufficient — but the Playbook, if versioned, will strain the model.

### 3.3 Immutability & ratification (as actually enforced)

**Enforcement layers:**

1. **PublishGate state machine** — `content_tool.content_complete` flips `status` → `completed`, fires PublishGate (see MEMORY.md `feedback_deliverable_status_via_content_complete`). Bypasses `Deliverable.status.choices` since `completed` is undeclared at Python layer.
2. **0010 §6 policy** — states that `status=completed` deliverables are immutable-on-write.
3. **No enforcement at ORM level** — `Deliverable.save()` on a completed row is not blocked by model constraint or signal (I did not confirm this by attempting a write, per non-mod constraint; but §6 language implies policy-based, not enforcement-based).
4. **`content_hash` NOT populated on 0199** — the SHA-256 `81ff5547…` is recorded in the S2707 handoff §6 as external attestation, not in the row's `content_hash` field.

**Ratification records** are `deliverable_type='ratification_record'` (5 rows), but three of them (0110/0120/0130 ratifications) landed as `deliverable_type='document'` per historical drift (0199 §6). This is a known governance-layer defect and a candidate for the Playbook's provenance discipline.

### 3.4 Versioning (as actually used)

**No modeled versioning.** No `version` field on Deliverable. Versioning is done by:

- Creating a new deliverable with a version-encoded title (`MANIFEST_v20260707` — one workspace example).
- `cloned_from` FK captures copy-lineage but is not the same as semantic version chain.
- `metadata` JSONField could carry `{version: "1.0", supersedes: "…"}` but no convention exists.

If the Playbook is going to have v1.0, v1.1, v1.2 revisions with SIGN + ratification cycles between them, the workspace needs a versioning convention.

### 3.5 Enumeration / schema defects surfaced during inventory

1. **`deliverable_type` enum undercounts.** Governance types (`adr`, `cycle_open`, `cycle_close`, `ratification_record`) exist as free strings in DB but are NOT in the Python `choices` list. Django admin/form validation blocks them; ORM writes accept them.
2. **`status` enum undercounts.** Declared 4 values (`draft`, `ready`, `published`, `archived`); actual DB has `completed` too.
3. **`category` is uncontrolled vocabulary.** In this one workspace: `operational`, `governance`, `Governance` (case!), `ratification_record`, `repo_profile`, empty.
4. **`content_hash` unused on immutable rows.** Immutability attestation is externalized to handoff text.
5. **`parent_object_id` unused across governance.** All hierarchy is title-string-encoded.

Any Playbook-hosting decision needs to either accept these defects, or codify a Playbook rule that fixes them.

### 3.6 Cross-document references

**No modeled reference edges.** 0199 references 0100 / 0110-0150 / ratification records / handoffs — all references are **markdown links or free-text UUIDs inside the body**. No `references` M2M, no back-references. Broken-link detection would require content parsing.

### 3.7 Discoverability

Two discovery routes both exist and are documented in CLAUDE.md:

- **PA route:** `deliverable_tool.list workspace_id=… show_all=true` (Rigby-mediated)
- **ORM route:** `Deliverable.objects.filter(workspace_id=…)`

**Workspace-source is mirrored into RAG** (`content.Document` where `source='workspace'` → 7 rows, `canonical_authority='workspace_canonical'`). So retrieval via Rigby vector search works.

### 3.8 Retrieval characteristics

Cycle 1A ADR-0130 established **authority-aware retrieval** — workspace-canonical docs win over repo-canonical when the same content mirrors both surfaces. This is the substrate that makes hybrid architectures viable: RAG doesn't have to pick between workspace and repo, it can prefer one when both exist.

### 3.9 Permissions

`data_sensitivity='internal'` on 0199 — coarse. No per-role or per-user access control observed on governance deliverables. Effectively single-tenant (Chris + platform automation).

## Phase 4 — Knowledge Layer Architecture

Using the inventory, here is the architectural model for where different knowledge classes should live. This is a proposal, not the current state — but it is grounded in what Cycle 1A already established.

### Layer 1 — Constitutional Knowledge

**What lives here:** Engineering Playbook, ADRs (0110–0150 today; 0200+ tomorrow), Ratification Records, Evidence Ledgers, Cycle open/close records, canonical governance (RAR methodology, Research OS).

**Ownership:** Chris (ratifier) + Claude/Rigby (author & maintainer).

**Home:** **Workspace `a9a16593-…`** — already de facto true post-Cycle-1A.

**Source of truth:** Workspace deliverable content is authoritative. Repository files, if any, are **mirrors**.

**Synchronization direction:** Workspace → RAG (via KFI-1 mirror pattern; workspace-source Documents flagged `canonical_authority='workspace_canonical'`); Workspace → Repo (via optional pointer files like the CLAUDE.md L7 anchor). **Never repo → workspace for L1.**

**Mirrored:** RAG (7 rows today, growing), CLAUDE.md L7 anchor (a pointer, not a mirror — pointer stability is enforced by CLAUDE.md contract in the L7 blockquote).

**Never duplicated:** Full content of L1 artifacts must not be copy-pasted into repo files. Only pointer + workspace UUID + reason-to-fetch belongs in the repo mirror.

**Immutable vs editable:** Post-ratification: **immutable-on-write** via `content_tool.content_complete` + PublishGate. Pre-ratification drafts are editable; ratification is the transition point.

**Consumer:** Governance (Chris + SIGN cycle). Operational consumers reach it via RAG or CLAUDE.md anchor, not by direct read.

### Layer 2 — Operational Documentation

**What lives here:** `CLAUDE.md` itself, `MEMORY.md`, `00-START-NEXT-SESSION.md`, `docs/handoffs/*`, `docs/topics/*`, runbooks, deployment docs, developer onboarding, `docs/PLATFORM_WHAT_IT_IS.md`, `docs/PLATFORM_INVENTORY.md`.

**Ownership:** Claude Code + the human developer at the terminal.

**Home:** **Repository** (`/docs/` primarily; `/CLAUDE.md` and `/MEMORY.md` at repo root).

**Source of truth:** Repository files. Handoffs are historical (write-once, edit-rare); topics are current-state (regenerable).

**Synchronization direction:** Repo → RAG (via `build_docs_index` → `build_rag_corpus` → `sync_docs_index_to_documents` → `embed_documents` cascade; MEMORY.md `feedback_docs_pipeline_4_step_cascade`). **Never RAG → repo.**

**Immutable vs editable:** Mostly editable. Handoffs are convention-immutable (`docs/handoffs/SESSION_XXXX_*.md`) but not enforced.

**Consumer:** Operational (Claude at session start; humans debugging).

### Layer 3 — Repository

**What lives here:** All code, migrations, tests, `Makefile`, `Procfile`, config, and Layer 2 documentation.

**Ownership:** Engineering team (Chris + Claude).

**Source of truth:** Git. `main` is the deployed state; feature branches are proposed state.

**Immutable vs editable:** Editable via PR + merge. Immutability = commit hash + tag chain.

**Consumer:** Everyone.

### Layer 4 — Runtime

**What lives here:** PostgreSQL (Deliverables, Documents, everything else), Redis (Celery broker, cache), Beat (scheduled tasks), running processes.

**Ownership:** Platform automation (Rigby + Celery workers).

**Source of truth:** Whatever the process is producing right now.

**Consumer:** Everyone via API/PA/RAG.

### Layer 5 — RAG

**What lives here:** `content.Document` + `content.DocumentEmbedding` — the retrieval-optimized mirror of L1 + L2.

**Ownership:** Platform automation (cascade jobs).

**Source of truth:** NONE — RAG is derived. Never write L1 or L2 truth directly to `content.Document`. Cascade populates it.

**Governance metadata:** `canonical_authority` field (ADR-0120) distinguishes `repo_canonical` / `workspace_canonical` / `derived`. ADR-0130 makes retrieval authority-aware.

**Consumer:** Rigby (RAG search), PA answers, semantic discovery.

## Phase 5 — Architectural Options

I compare three architectures for the **Engineering Playbook specifically**, holding the rest of the L1–L5 model above constant.

### Option A — Playbook in Repository (`/docs/ENGINEERING_PLAYBOOK.md`); workspace secondary

**Structure:** Playbook lives as a markdown file in the repo. Workspace holds an optional reference deliverable.

**Strengths:**
- Zero new machinery — reuses `/docs/` pipeline already exercised for 2,986 docs.
- Session-open bootstrap is trivial (Claude reads a file; no PA auth needed for Phase 0).
- Version history is Git-native (commits, tags, PRs). Diffs are cheap.
- Discoverability via file path is stable and human-obvious.
- Consistent with Layer-2 pattern for CLAUDE.md, MEMORY.md, 00-START.

**Weaknesses:**
- **Reverses Cycle 1A migration.** Cycle 1A explicitly moved constitutional artifacts OUT of `/docs/` INTO workspace. Placing the Playbook back in `/docs/` breaks the L1/L2 separation just established.
- **No immutable-on-write.** Ratified Playbook v1.0 is a git tag, not a PublishGate state. Anyone with commit access can amend v1.0 in a follow-up commit — the historical ratified content is only recoverable by `git show <tag>`, not surfaced as a permanent row.
- **Ratification record has no anchor.** How does the workspace express "we ratified `/docs/ENGINEERING_PLAYBOOK.md@v1.0`"? Currently the workspace's ratification-record pattern names a UUID (`c883ebef-…` names `53756b1c-…`). A ratification record naming a git tag is a new pattern.
- **RAG mirror direction inverts.** Instead of workspace→RAG, we'd have repo→RAG for L1 content — regressing the ADR-0120 `canonical_authority='workspace_canonical'` posture for the most consequential doc.
- **Provenance classification (PIC-10) gets harder.** PIC-10 wants every ratified statement classified by evidence type. Markdown files support this via convention only, not via structured fields.

**Operational complexity:** Low.
**Maintenance burden:** Low upfront; high long-term (drift risk between repo Playbook and workspace governance records).
**Retrieval implications:** Playbook retrieved as `canonical_authority='repo_canonical'` — inconsistent with 0110–0150 which are `workspace_canonical`.
**RAG implications:** Requires cascade discipline (already stable).
**Implementation complexity:** Trivial. Write the file.
**Future scalability:** Poor. Each revision cycle (v1.1, v1.2) has no ratification-record anchor — the audit trail relies on Git commit messages, which Cycle 1A already found insufficient (see G1 finding in 0199 §8).
**Compatibility with Cycle 1A:** **Poor.** Directly contradicts KFI-1/KFI-2/KFI-5 direction of travel.

### Option B — Playbook in Workspace; repository secondary or absent

**Structure:** Playbook is a workspace deliverable (`0200_ENGINEERING_PLAYBOOK` or similar). Repo has no copy at all, or only a `docs/ENGINEERING_PLAYBOOK.md` stub that says "canonical version at workspace `<uuid>`."

**Strengths:**
- **Direct continuation of Cycle 1A pattern.** Same as 0110–0150. Ratification, immutability, PublishGate all reuse mechanisms that just shipped.
- **Immutable-on-write is real.** v1.0 becomes `status=completed`; revisions require SIGN + Chris ratification per 0199 methodology.
- **Ratification records already work for this shape.** `RATIFICATION_20260710_0200_ENGINEERING_PLAYBOOK_v1_0` is a straight-line application of the ratification-record pattern.
- **Provenance classification (PIC-10) is natively supported** via `metadata` JSONField (per §3.11 opportunity list).
- **RAG posture is correct.** Playbook is `canonical_authority='workspace_canonical'`; consistent with the rest of L1.
- **Version chain has a modeling seat.** `parent_object_id` on v1.1 pointing at v1.0 (currently unused per §3.2 — a green-field opportunity).

**Weaknesses:**
- **Session-open bootstrap gets heavier.** Claude at Phase 0 needs to fetch the Playbook via ORM or PA before its methodology applies. Today's Phase 0 is `Read` the repo file. Tomorrow's Phase 0 needs `python manage.py shell` or `pa_local.sh` before reading the constitution.
- **Local-dev friction.** Developers not running the platform (e.g., cloning fresh) can't read the Playbook without a working Django shell + local DB.
- **Diff experience is worse.** Workspace deliverable diffs are not git diffs. Comparing v1.0 vs v1.1 requires either a materialized snapshot or a custom diff view.
- **Discovery outside the platform is harder.** GitHub search does not index workspace content.

**Operational complexity:** Medium — same as Cycle 1A ADRs (proven).
**Maintenance burden:** Medium. Requires cascade discipline (already established).
**Retrieval implications:** Best-case — workspace-canonical, authority-aware retrieval works out of the box.
**RAG implications:** Same mirror pattern as KFI-1.
**Implementation complexity:** Low — reuses the exact primitives Cycle 1A shipped.
**Future scalability:** Good. Version-chain and provenance modeling have modeling seats even if not yet used.
**Compatibility with Cycle 1A:** **Excellent.** Direct continuation.

### Option C — Hybrid (Playbook workspace-canonical + repo pointer file)

**Structure:** Playbook body lives in workspace (per Option B). A repo file at a stable path (e.g., `docs/ENGINEERING_PLAYBOOK_ANCHOR.md`) is a **pointer** with:
- Workspace UUID of ratified version
- Short 100-line executive summary and version banner
- Fetch instructions ("read full body via `deliverable_tool.get id=…` or ORM")
- Never edited by hand — regenerated from workspace via a cascade step

Modeled directly on the CLAUDE.md L7 anchor pattern established by KFI-5.

**Strengths:**
- **Best of both.** Workspace has canonical + immutable + ratifiable body. Repo has cheap Phase-0-bootstrap access to the pointer + summary.
- **CLAUDE.md L7 anchor already trained the pattern.** No new invention required. Cycle 1A explicitly established that `CLAUDE.md` can point at workspace deliverables without moving the truth.
- **Phase 0 stays cheap.** Claude reads the anchor file at session start; PA/ORM only needed if the anchor summary is insufficient (which it rarely is for Phase 0 orientation).
- **RAG has both.** Anchor file is `canonical_authority='repo_canonical'`; workspace body is `canonical_authority='workspace_canonical'`. Authority-aware retrieval (ADR-0130) prefers workspace. Rigby search Just Works.
- **Version banner in anchor is human-obvious.** "Currently ratified: v1.2 (workspace `<uuid>`, ratified 2026-08-15)."
- **Regenerable via a Playbook cascade step.** Same shape as the 4-step docs cascade — anchor file becomes an autogen artifact regenerated post-ratification, guarded by `<!-- DOC-AUTOGEN -->` comment (already used by `docs/INDEX.md`).

**Weaknesses:**
- **Two things to keep in sync.** Every Playbook revision must run the anchor-regeneration cascade or the anchor's version banner drifts. Cycle 1A already established the cascade discipline (`feedback_docs_cascade_at_every_close`), so the muscle exists — but it's another cascade step.
- **Requires new tooling.** A `regenerate_playbook_anchor` management command (or extension of `refresh_doc_inventory_blocks`). Small but non-zero implementation.
- **Anchor summary drift.** If the anchor's 100-line summary rewords the workspace body, "verbatim provenance" (PIC-10 substance) needs a rule: anchor summaries are engineering summaries, not verbatim quotations — must be labeled as such.

**Operational complexity:** Medium — one extra cascade step over Option B.
**Maintenance burden:** Medium — but every step in the maintenance chain reuses primitives already shipped in Cycle 1A.
**Retrieval implications:** Best. Both mirrors + authority-aware retrieval + a repo-side pointer for cheap discovery.
**RAG implications:** Same as Option B plus the anchor becomes searchable in `canonical_authority='repo_canonical'` — good for humans grepping the repo.
**Implementation complexity:** Low-medium — Option B + a small regeneration script.
**Future scalability:** Excellent. Every future L1 artifact can adopt the same anchor pattern.
**Compatibility with Cycle 1A:** **Excellent — and reinforcing.** This IS the pattern KFI-5 already trained on CLAUDE.md L7. Doing it for the Playbook makes it a template.

### Challenging the recommendation (Option C)

Before I recommend Option C, I want to attack it:

1. **"Isn't this over-engineering? Just put it in repo."** — It would be over-engineering for a one-off doc. But the Playbook is by definition the constitution; every future ADR revision will reference it; every future SIGN cycle will consult it. Under-engineering the constitution costs more than the marginal cascade step.
2. **"The anchor pattern is unproven."** — It ships in exactly one place today (CLAUDE.md L7). But it shipped as KFI-5 with ratification and cascade discipline. Applying it to a second artifact is the natural next iteration; if the pattern is going to be codified in the Playbook itself (highly likely — it's the shape KFI-5 taught us), the Playbook should adopt it first as a demonstration.
3. **"What if the workspace layer is fragile?"** — Cycle 1A stress-tested it. 25 deliverables written and ratified across multiple sessions. PublishGate fired cleanly. `content_tool.content_complete` behaved. Rigby + ORM discovery both work. The layer is production-grade for governance.
4. **"Won't the anchor summary become the de facto canonical version?"** — Only if we let it. The cascade regenerates it from workspace; humans never edit it directly. Same discipline as `docs/INDEX.md` (autogen, guarded by DOC-AUTOGEN comment enforced by `scripts/verify_repo_guardrails.py`).
5. **"What about Option B, cleaner?"** — Option B is defensible. The only reason I prefer C is that CLAUDE.md L7 anchor already exists — introducing Playbook without a matching anchor creates an inconsistency (why does the CLAUDE.md L7 anchor point at workspace but the Playbook doesn't?). C makes the L1 pattern uniform across all constitutional artifacts.

Option C survives the attack.

## Recommendation

**Option C — Hybrid: Playbook body workspace-canonical (workspace `a9a16593-…`); repository holds an autogen anchor file that names the ratified version.**

**Evidence for this recommendation** (not preference):

1. **Cycle 1A established the pattern.** KFI-1/2/5 explicitly moved constitutional artifacts to workspace-canonical and demonstrated the CLAUDE.md L7 pointer anchor. Any recommendation that ignores this pattern trades a known-shipped-good foundation for a new invention.
2. **The workspace has every primitive the Playbook needs** (immutable-on-write, ratification records, `metadata` for PIC-10 provenance classification, `parent_object_id` for version chain, RAG mirror with `canonical_authority='workspace_canonical'`) — §3.11 opportunity list.
3. **Repo pointer solves the only real cost of Option B** (heavier Phase-0 bootstrap). CLAUDE.md L7 anchor proves the pattern is cheap.
4. **PIC-10 (Provenance Classification Standard) is the flagship discipline the Playbook must codify.** It maps naturally onto Deliverable `metadata` JSONField. Markdown-in-repo would require inventing structured metadata as YAML front-matter — a strictly worse substrate.
5. **Session 1234 4-step cascade discipline** (`feedback_docs_pipeline_4_step_cascade`) is already the muscle memory; the anchor regeneration extends this muscle by one step, not a novel discipline.
6. **Consistency wins.** After the Playbook lands under Option C, every L1 artifact will share the same shape: workspace body + repo pointer + RAG mirror. That uniformity is a governance property in its own right — the constitution should not be an exception to the constitutional pattern.

**Why not Option B alone:** the CLAUDE.md L7 anchor already exists. Introducing a workspace-only Playbook without a matching anchor creates an inconsistency inside the L1 layer. The anchor pattern must apply to the Playbook, not just to CLAUDE.md.

**Why not Option A:** it reverses the direction Cycle 1A explicitly established, sacrifices immutable-on-write, and lacks a native seat for provenance classification. Every strength of Option A (git diff, GitHub search, session-open cheapness) is preserved by Option C via the anchor.

If this differs from how Donkey Betz currently operates: **it doesn't materially differ.** Cycle 1A already migrated the constitution to the workspace. Option C is the continuation, not a departure. The only novelty is adding an anchor for the Playbook — which is the exact pattern CLAUDE.md L7 already models.
