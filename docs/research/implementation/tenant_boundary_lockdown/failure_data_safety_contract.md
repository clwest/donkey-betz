## §1. Scope + Non-Scope

### §1.1 In-Scope

- **What:** the shape + content of the response body returned to a user (human or programmatic client) when an HTTP request produces an error (any non-2xx response) or a WebSocket connection closes with code >= 4000. **Includes 200-status async status endpoints that encode failure in the response body** (Rigby S2742 contract SIGN §1 — the semantic is "user-facing error surface," not "non-2xx status code")
- **Where:** every DRF view, every non-DRF Django view (including plain function views), every custom middleware error path, every 4xx / 5xx template render, every streaming (SSE) chunk that surfaces an error, every async task failure surface returned to a user via HTTP polling / notification
- **Governs:** user-facing envelope + operator-side envelope + `support_code` format + `trace_lookup` operator access rule + enforcement layering + regression-suite schema

### §1.2 Out-of-Scope

- **Success-path data leakage** (e.g., list endpoints returning too many rows or cross-tenant counts). Handled by the regression suite in `tests/security/test_cross_tenant_regression.py` — see I-0301 scoping §5.2.
- **Frontend rendering** of error responses. Frontend is expected to consume the envelope as-is; frontend polish is not I-0301 scope.
- **Django default 500 pages generated by `DEBUG=False`**. Django already generates generic content — but the regression suite verifies they leak nothing at test time.
- **Non-error responses that carry a `support_code` for observability** (e.g., success responses that emit a trace ID). Those are RUR-C2 scope for the traceability substrate; this contract only governs error-path emissions.
- **RUR-C6 cost enforcement breach responses** — those are error responses that MUST conform to this contract (i.e., contract applies), but the specific `reason_code = 'cost_cap_exceeded'` classification is defined in RUR-C6 scope.
- **Semantic-quality failures** ("succeeded but wrong") per Chris Q6 D-verdict — those are post-alpha; not enforced by this contract.

## §2. Governing Principles

The contract exists to prevent user-facing error surfaces from becoming an exfiltration path OR a debugging leak. Every rule below traces back to at least one of these principles:

- **P1 — Tenant isolation.** No user-facing error surface may expose data derived from a foreign workspace / user / conversation / deliverable / execution.
- **P2 — Substrate opacity.** No user-facing error surface may reveal internal file paths, module paths, credential material, provider request bodies, or exception messages that could inform an attacker about the substrate.
- **P3 — Operator sufficiency.** Operators must be able to diagnose failures from durable telemetry within the SLA (<2 min from `support_code`). The contract satisfies this via the operator-side envelope, not by leaking to the user.
- **P4 — Support handshake.** Users need enough information to file a support ticket and to know whether to retry. The contract provides this via `support_code`, `human_message`, `reason_code`, `retryable`, `terminal_state`.
- **P5 — Access-controlled diagnostics.** Even operator access to full trace context is tenant-scoped — support tooling is not itself an exfiltration path.

Where a specific rule below cites `(P#)`, it maps to the principle above.

## §3. User-Facing Error Envelope

### §3.1 — Permitted Fields

The response body to a user MAY contain ONLY the following top-level fields:

| Field | Type | Required? | Constraint |
|---|---|---|---|
| `support_code` | string | **Required** | Format per §5; opaque to user |
| `reason_code` | string | **Required** | Enumerated (§4); safe-by-design token, never a free-form message |
| `human_message` | string | **Required** | Locale-appropriate copy; MUST NOT contain foreign-workspace identifiers, filesystem paths, exception messages, provider names, or model names |
| `retryable` | boolean | **Required** | Client uses this to decide whether to auto-retry (with backoff) |
| `terminal_state` | string | **Required** | Enum: `FAILED`, `CANCELLED`, `DENIED`, `RATE_LIMITED`, `BUSY` |
| `timestamp` | string (ISO 8601, UTC) | Optional | If present, represents **server-generated request handling time** (not echoed from any client input; not row-created time from any foreign row); MUST NOT be derived from foreign-workspace data (P1) |
| `retry_after_seconds` | integer | Optional | Only present when `terminal_state == RATE_LIMITED` or `BUSY`; a hint, not a guarantee |

**Nothing else.** Additional fields are a contract violation.

### §3.2 — Prohibited Content

These MUST NOT appear anywhere in the user-facing response body, including nested in any allowed field:

| Prohibited item | Principle | Why prohibited |
|---|---|---|
| Foreign-workspace data (any field derived from another workspace's row) | P1 | Cross-tenant leakage |
| Raw model payloads (LLM prompt, LLM response, tool call args, tool call output) | P2 | Substrate + tenant leakage combined |
| User prompts or conversation contents — **unconditionally** (Rigby S2742 contract SIGN §4 material amendment) | P1 + P2 | Prior draft carried a "unless classified safe at field level" loophole; no such field-level classification mechanism exists in this contract, so the loophole was untestable. Removed. Prompts / conversation contents MUST NOT appear in the user-facing envelope, period. If a user needs to see their own message echoed back, the frontend does that from local state, not from the error envelope. |
| Filesystem paths (absolute or relative — `core/tasks.py`, `workspaces/*`, `docs/*`, etc.) | P2 | Substrate leak |
| Secrets or credentials (API keys, session tokens, HMAC secrets, hashed values) | P2 | Credential leak |
| Internal stack traces (Python traceback, Django ORM error paths) | P2 | Substrate leak |
| Raw exception values containing tenant data (`Exception: workspace_id=<foreign-uuid> denied`) | P1 + P2 | Both |
| **Free-form `exception_message`** in any user-facing surface, even sanitized (Rigby S2742 SIGN §6) | P2 | Sanitization is a footgun class we do not attempt; the `reason_code` enum + safe `human_message` replaces it |
| Unrestricted serialized objects (`repr(obj)`, `str(model_instance)`) | P1 + P2 | Both |
| Internal provider request bodies (OpenAI / Anthropic request payloads) | P2 | Substrate leak |
| **Correlation identifiers that could enable cross-tenant inference if globally visible** (Rigby S2742 SIGN §6) | P1 | `trace_id` in particular MUST NOT be surfaced to the user if the ID is globally visible across tenants; users get `support_code` only |
| Provider names or model names (e.g., "gpt-5.2", "claude-opus", "OpenAI") | P2 | Substrate leak; may correlate with cost/capability inference |
| Internal task queue names / worker hostnames | P2 | Substrate leak |
| Debug flags or environment names (`DEBUG=True`, `env=staging`) | P2 | Substrate leak |
| Cost or token counts (except in `reason_code = 'cost_cap_exceeded'` where a scoped hint may be permitted per RUR-C6 spec) | P1 + P2 | Cost inference across tenants |

### §3.3 — Locale + Length Constraints

- `human_message` MUST be <= 500 characters. Longer messages are truncated at the enforcement layer with an ellipsis; a truncated message never carries prohibited content that appeared beyond the truncation point.
- `human_message` MUST be locale-appropriate. The default English messages are defined in the reason_code enum (§4); other locales are out of scope for I-0301 (I-0301 delivers English only).
- `support_code` and `reason_code` are ASCII-only.

## §4. `reason_code` Enum

The initial enumerated set below is exhaustive for I-0301. Additions require an amendment to this contract (post-freeze) and a new ratification record.

| `reason_code` | Default `human_message` (English) | `retryable` | `terminal_state` | Typical HTTP status |
|---|---|---|---|---|
| `not_found` | The requested resource could not be found. | false | FAILED | 404 |
| `permission_denied` | You do not have permission to access that resource. | false | DENIED | 403 |
| `not_authenticated` | You must be signed in to do that. | false | DENIED | 401 |
| `invalid_input` | The request contained invalid data. | false | FAILED | 400 |
| _(differentiator: `invalid_input` = parse / schema shape failure; `validation_error` = business-rule failure — Rigby S2742 contract SIGN §6)_ | | | | |
| `workspace_not_accessible` | That workspace isn't accessible from your account. | false | DENIED | 403 |
| `rate_limited` | Too many requests. Please wait a moment and try again. | true | RATE_LIMITED | 429 |
| `busy` | The system is busy. Please try again shortly. | true | BUSY | 503 |
| `upstream_provider_error` | An upstream service is temporarily unavailable. | true | FAILED | 502 |
| `upstream_provider_timeout` | An upstream service did not respond in time. | true | FAILED | 504 |
| `cost_cap_exceeded` | This operation exceeds the configured cost cap for your workspace. | false | DENIED | 402 |
| `cancelled` | The operation was cancelled. | false | CANCELLED | 200 (async status endpoint) |
| `internal_error` | Something went wrong on our side. Support has been notified. | false | FAILED | 500 |
| `unavailable` | This feature is temporarily unavailable. | false | FAILED | 503 |
| `validation_error` | The request failed validation. | false | FAILED | 400 |

**Enum discipline:** the `internal_error` code is the fallback of last resort. Any exception path that would produce an unhandled error MUST resolve to `internal_error` at the enforcement layer; the exception details go to the operator envelope only.

## §5. `support_code` Format

### §5.1 — Format Specification

`RUR-<COMPONENT>-<yyMMdd>-<opaque-hex>`

- `RUR` — literal prefix identifying the Real User Readiness program
- `<COMPONENT>` — uppercase alpha; identifies the failure component. Enumerated: `AUTH`, `PERM`, `WORKSPACE`, `RATE`, `BUSY`, `UPSTREAM`, `COST`, `CANCEL`, `INTERNAL`, `VALIDATE`, `INPUT`, `MISSING`
- `<yyMMdd>` — 6-digit date in UTC; represents the day the failure was generated
- `<opaque-hex>` — 4-hex-char opaque identifier; not derived from tenant data; generated via `secrets.token_hex(2)`

Example: `RUR-AUTH-260710-a4f2`

### §5.2 — Privacy Assessment (per Rigby S2742 SIGN §6.3)

- **Cross-tenant leak?** No. The code contains no tenant identifier.
- **Substrate leak?** Minimal. The code reveals: (a) which program produced the failure (RUR), (b) which failure component (AUTH etc.), and (c) rough day. This is intentional — operators need the component to route the ticket. Users need the code to file a ticket.
- **Timing leak?** The date component reveals rough incident timing. **Acceptable for gated alpha.** Post-alpha hardening candidates: drop the date component or replace with week-of-year. Not required for Wave 1.

### §5.3 — Uniqueness

`secrets.token_hex(2)` = 16 bits of entropy = 65,536 codes per `(component, day)` bucket. Collision probability is negligible for the gated alpha cohort scale (~10 users). If the platform later needs stronger guarantees, `token_hex(2)` widens to `token_hex(4)` = 32 bits without changing the format shape.

### §5.4 — Stability

Once emitted, a `support_code` is stable across the failure event:
- The same code is returned to the user in the response envelope
- The same code is written to the operator-side `OpsRunEvent` row
- Operators use the code to look up the trace context via `trace_lookup` (§6.3)

The user never sees the `trace_id`. The operator never quotes the `trace_id` back to the user.

## §6. Operator-Side Diagnostic Envelope

### §6.1 — Envelope Content

Every failure event produces a durable `OpsRunEvent` row (or equivalent structured telemetry row) with the following operator-facing content. The row itself is tenant-scoped; access is controlled per §6.2.

```
OpsRunEvent (tenant-scoped write):
  support_code           <same as user-facing envelope §3.1>
  trace_id               <propagated end-to-end; operator-only>
  reason_code            <enumerated per §4>
  exception_class        <internal, full detail; operator-only>
  exception_message      <internal, full detail; operator-only; may contain tenant identifiers>
  request_context:
    user_id              <request-time user; operator-only>
    workspace_id         <request-time workspace; operator-only>
    endpoint             <route path>
    http_method
    query_params_redacted  <query params with any string > 200 chars truncated + credentials stripped>
    request_id             <upstream request identifier if present>
  provider_context:
    provider_name          <e.g., "openai"; operator-only>
    model                  <e.g., "gpt-5.2"; operator-only>
    tokens_estimate        <token count if applicable>
    cost_estimate_usd      <cost if applicable>
  timing:
    request_started_at
    request_completed_at
    request_duration_ms
```

### §6.2 — Access Control (per Rigby S2742 SIGN §6 material amendment)

`trace_lookup` and any operator dashboard that reads `OpsRunEvent` MUST enforce:

1. **Operator-only.** Callers without an operator role receive `permission_denied`. This is enforced at the view / management command layer, not just documented.
2. **Tenant-scoped.** Operators can only retrieve traces for tenants / workspaces they are authorized to support. A workspace-B operator cannot see workspace-A trace details even by knowing the `support_code`. Enforcement mechanism: the operator's role includes a `supported_workspace_ids` set; `OpsRunEvent` rows outside that set are filtered from queries.
3. **No leak-back.** `trace_lookup` output MUST NOT include foreign identifiers in a form an operator could paste back to a user to enable exfiltration. Specifically: `trace_lookup` output for a support ticket includes the requester's own workspace_id + user_id, but not any *other* workspace's identifiers unless the operator is authorized for those tenants too.
4. **Alpha-level enforcement.** If a code-level `supported_workspace_ids` RBAC system is not yet implemented at Phase 3 open, the tenant-scope requirement is enforced **procedurally** — operator runbook + operator agreement + logged access with audit trail. This is acceptable for alpha; the code-level enforcement plan tracks as a follow-on and is required before self-serve (post-alpha).
5. **Audit trail.** Every `trace_lookup` invocation writes an audit row: `(operator_id, support_code, timestamp, granted OR denied, reason)`. Denied lookups are just as important as granted ones for detecting probing.

### §6.3 — Operator Trace Lookup Tool

`python manage.py trace_lookup <support_code>` — the canonical operator lookup path.

- Input: a `support_code` (typically quoted by a user in a support ticket)
- Auth: the calling operator must have a role that includes the tenant of the `OpsRunEvent` row; management-command auth uses the invoking OS user + operator role table
- Output: the operator-side envelope from §6.1, subject to the access rules in §6.2
- SLA: returns in < 10 seconds wall-clock (RUR-C2 exit criterion E9 companion)
- Audit: every invocation writes to the audit trail per §6.2.5

The command lives in RUR-C2 scope for implementation; this contract defines its access contract.

## §7. Component Coverage — Where the Contract Applies

The contract governs error surfaces from every layer of the HTTP + WebSocket stack.

### §7.1 — DRF Views

- Every DRF view returning a non-2xx response
- Enforcement point: `REST_FRAMEWORK.EXCEPTION_HANDLER` custom handler that catches all exceptions raised inside DRF view code and produces the §3.1 envelope

### §7.2 — Non-DRF Django Views

- Every non-DRF Django view (plain function view + class-based generic view) returning a non-2xx response
- Enforcement point: a custom exception middleware placed early in `MIDDLEWARE` that catches uncaught exceptions from non-DRF paths and produces the §3.1 envelope
- Also covers plain function views decorated with `@csrf_exempt` (the 718-file follow-on scope from Phase 1)

### §7.3 — Template-Rendered Error Pages

- Custom `403.html` / `404.html` / `500.html` templates (if present in `templates/`) MUST render only the §3.1 permitted fields (Django's own defaults are already generic + safe)
- Enforcement point: template review at Phase 3; regression suite verifies template output shape

### §7.4 — Streaming Responses

- Server-Sent Events (SSE) and any chunked-transfer streaming where an error can surface mid-stream
- Each error chunk MUST conform to the §3.1 envelope shape
- **Phase 3 must first audit** whether SSE / streaming error surfaces exist in the alpha user path (Rigby S2742 contract SIGN §9). If any exist, the streaming-response wrapper utility is mandatory at Phase 3. If none exist in the alpha path, wrapper implementation may defer to post-alpha with a documented follow-on ticket.

### §7.5 — Async Status Endpoints

- Endpoints that report the status of an async task (`GET /api/tasks/<id>/status/`) where the reported status includes a terminal failure reason
- MUST conform to §3.1
- Enforcement point: the async status view's error surface uses the same envelope construction

### §7.6 — WebSocket Close Codes

- Every WebSocket connection that closes with code >= 4000 (application-defined error range)
- The close reason (WebSocket close frame reason string) MUST conform to a safe shortlist: `permission_denied`, `not_authenticated`, `rate_limited`, `busy`, `upstream_error`, `internal_error`
- The full `support_code + reason_code + human_message` bundle is sent as the last frame BEFORE the close, so the client can render it
- Enforcement point: consumer close wrapper (RUR-C5 scope; contract defines the shape here)

## §8. Enforcement Layering

Four enforcement layers combine to produce the contract's actual reliability. **No single layer is sufficient.**

### §8.1 — Layer 1: DRF Exception Handler

- `REST_FRAMEWORK.EXCEPTION_HANDLER` set to a custom handler
- Catches DRF-raised exceptions (`APIException` subclasses) + arbitrary Python exceptions raised inside DRF view code
- Maps to the §3.1 envelope; writes the §6.1 operator envelope; returns the response
- Live in `core/security/error_envelope.py::drf_exception_handler`

### §8.2 — Layer 2: Django Middleware

- Custom `RURErrorEnvelopeMiddleware` placed early in `MIDDLEWARE`
- Catches uncaught exceptions from non-DRF views (function views, generic views, static routes)
- Same envelope construction as Layer 1
- Live in `core/security/error_envelope.py::RURErrorEnvelopeMiddleware`

### §8.3 — Layer 3: Template Overrides

- Custom 4xx / 5xx templates conform to the §3.1 envelope shape as HTML
- Placeholder tokens (`{{ support_code }}`, `{{ human_message }}`, etc.) rendered from the envelope
- Django's defaults left in place for the fallback path (they are already generic)

### §8.4 — Layer 4: Regression Suite

- `tests/security/test_failure_envelope_conformance.py` (new; scaffolded in Phase 3)
- Fires deliberately-broken requests + WebSocket connects + streaming errors
- For each response: schema-asserts the body has ONLY the §3.1 permitted fields (JSON-schema based)
- For each response: asserts the body does NOT contain any prohibited-content marker (via regex over the JSON representation: no filesystem-looking paths, no `Traceback`, no `Exception:`, no provider names from a known list, etc.)
- CI-blocking: any conformance failure blocks the PR

**Any response body that reaches a user without passing through at least one enforcement layer's construction is a contract violation.** The regression suite catches the layers being bypassed.

## §9. Regression Suite Schema (probes)

The regression suite `tests/security/test_failure_envelope_conformance.py` MUST at minimum test the following probes:

### §9.1 — Positive Envelope Shape Probes

For each error response type (401, 403, 404, 429, 500, 502, 504, WS close 4xxx):
- Response body is valid JSON (except HTML template renders, which use a template-schema check)
- Response body contains all Required fields per §3.1
- No field in response body outside the §3.1 Permitted list
- `reason_code` is in the §4 enum
- `terminal_state` is in the §3.1 enum
- `support_code` matches the §5.1 format regex `^RUR-[A-Z]+-\d{6}-[0-9a-f]{4}$`
- `human_message` length <= 500 chars

### §9.2 — Prohibited-Content Probes

**Primary check (per Rigby S2742 contract SIGN §11):** JSON-schema validation against the §3.1 permitted field allowlist. Any field NOT in the allowlist is a failure. Any Required field missing is a failure. This catches the class "unexpected data smuggled in" comprehensively.

**Secondary check (regex substring):** for defense-in-depth, the full serialized body MUST NOT match any of:
- Filesystem path patterns (`/Users/`, `/home/`, `/app/`, `workspaces/`, `docs/`, `core/`, `.py`, `.json`)
- Stack-trace patterns (`Traceback`, `File "`, `raise`, `line \d+`)
- Exception-value patterns (`Exception:`, `Error:`, `ValueError:`, `TypeError:`)
- Provider-name patterns (case-insensitive; curated list): `openai`, `anthropic`, `gpt-`, `claude-`, `gemini`, `deepseek`
- Credential patterns (`sk-`, `Bearer `, hex strings > 32 chars)
- **UUID pattern anywhere in the body** — the permitted-field allowlist contains NO UUID-typed fields, so any UUID substring match is a violation regardless of ownership. This is simpler and stronger than "foreign UUIDs only" (Rigby S2742 contract SIGN §11 tightening).

### §9.3 — Cross-Tenant Probes

- User-A makes a request that fails → response body contains NO reference to user-B or workspace-B data
- User-A queries with a foreign workspace_id → response body has `reason_code = workspace_not_accessible` and NO leak of foreign row content
- User-A hits a rate limit → response includes `retry_after_seconds` but NO information about queue depth / other users' load

### §9.4 — Layer Coverage Probes

- Deliberately raise an exception inside a DRF view → Layer 1 envelope produced
- Deliberately raise an exception inside a non-DRF Django view → Layer 2 envelope produced
- Deliberately trigger a 404 from Django URL resolution → Layer 3 template render conforms
- Fire a WebSocket connect that will be denied → close frame reason is safe shortlist + last frame carries envelope

## §10. Amendment Discipline

Post-ratification, this contract is `frozen: true`. Changes are governed by:

- **Reason_code additions:** allowed via a new ratification record referencing this doc as `supersedes`. Rigby SIGN on the addition. Chris ratification.
- **Prohibited-content additions:** same process; additions strictly tighten the contract, do not relax it.
- **Permitted-field additions:** require a full Rigby SIGN + Chris ratification. Additions may relax the contract; extra scrutiny.
- **Enforcement-layer changes:** require a full Rigby SIGN + Chris ratification. Layer additions are permitted; layer removals require justification.
- **`support_code` format changes:** trigger a stability discussion — support codes emitted under old formats must remain lookupable via `trace_lookup` for at least 90 days post-format-change.

Discovered contract insufficiency during Phase 3 remediation routes back through this amendment discipline. Do NOT ship a Phase 3 exception surface that violates this contract and defer the fix; either the contract expands to cover the case, or the exception surface conforms.
